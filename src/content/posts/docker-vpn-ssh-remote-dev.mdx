Windows 的 UniVPN 客户端一次只能连接一套环境。我需要保留原来的 VPN，同时访问另一套内网，又不想多开一台 Windows 虚拟机，于是把额外的 UniVPN 放进 Docker。

现在采用的方案是：**每套 UniVPN 独占一个容器，Windows 通过 WireGuard 把指定目标的流量送进去。** 配好后，应用直接使用原始内网 IP，例如 `ssh your-user@10.80.0.11`；网页和 UDP 服务走同一条路径。

这条路线已经完成纯终端短信认证和 Windows 多协议实测。配套源码在 [JavaZeroo/univpn-docker-gateway](https://github.com/JavaZeroo/univpn-docker-gateway)。它仍是实验项目，下面说明具体用法和已经验证的范围。

## Windows 通过 WireGuard 接入独立的 UniVPN 容器

容器拥有独立的网络命名空间。UniVPN 创建的 `cnem_vnic`、内网路由和转发规则留在对应容器中。增加一套 VPN，就增加一个独立实例，分别配置账号、密钥、接入地址和 UDP 端口。

Windows 还需要到容器的网络入口。[Docker Desktop 的 Linux 容器网络位于虚拟机内部](https://docs.docker.com/desktop/features/networking/networking-how-tos/)，不能直接把容器 IP 当作 Windows 路由的下一跳。因此，这里通过发布到 `127.0.0.1` 的 UDP 端口接入 WireGuard。

<UniVpnArchitecture />

图中的**数据面**承载 SSH、HTTP、UDP 等业务：Windows 应用 → Windows WireGuard → localhost UDP → 容器 `wg0` → 转发与 SNAT → `cnem_vnic` → 内网目标。SNAT 将来源换成容器的 VPN 地址，让远端回包沿原路返回。

**控制面**负责登录和决定何时允许转发。`vpnctl` 在终端收取账号、密码和短信验证码，经本地控制接口交给 Python 服务，再通过 CSDK/RPC 控制官方 UniVPNCS。验证码续交到原来的引擎和登录会话。

后台守卫检查 VPN 接口、目标路由和真实业务探针。检查失败后，专属转发链切换为 DROP；正常流量还必须从 `wg0` 转向指定 VPN 接口，不能改从容器普通出口发走。状态变化有轮询和探针超时延迟。

WireGuard 只连接 Windows 与本机容器；访问远端环境仍由 UniVPN 完成。容器内的 `wg0` 是 Linux 内核接口，**不需要再运行一个 WireGuard 常驻进程或辅助容器**。[WireGuard 的网络命名空间说明](https://www.wireguard.com/netns/)解释了接口与命名空间的关系。

当前验证的厂商版本是 **10781.21.0.0831**，运行环境是 Ubuntu 22.04 / amd64。项目会校验安装包及引擎摘要，换版本或架构需要重新验证这条本地接口，不能直接忽略校验。

默认 Compose 使用 bridge 网络，额外授予 `NET_ADMIN` 和 `/dev/net/tun`，供引擎配置 VPN 网卡和路由；不使用 privileged 或宿主机网络。WireGuard 内核能力来自 Docker 的 Linux 环境，安装工具包本身不能替代它。

默认 `native` 镜像使用 Python 标准库，不安装 Qt、X11、Xvfb、DBus 或 VNC。厂商程序由用户自行下载后本地构建；项目不分发包含厂商程序的镜像或安装包。分层细节见仓库的[架构文档](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/docs/architecture.md)。

## Windows 接入需要先完成容器内的 VPN 认证

以下以 `10.80.0.11` 为示例目标，所有网关、密钥和地址都需要按自己的环境填写。准备好 Docker Desktop 的 Linux 容器环境，以及 [Windows 官方 WireGuard](https://www.wireguard.com/install/)。完整密钥生成与文件权限步骤见[快速开始](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/docs/quickstart.md)。

### 1. 克隆项目，自备厂商安装包

```powershell
git clone https://github.com/JavaZeroo/univpn-docker-gateway.git
Set-Location univpn-docker-gateway
New-Item -ItemType Directory -Force vendor, private | Out-Null
Copy-Item .env.example .env
```

从[联软官方下载页面](https://www.leagsoft.com/doc/article/103107.html)取得适用的 Linux 安装包，解压后的安装程序放到 `vendor/univpn.run`，然后计算摘要：

```powershell
Get-FileHash vendor/univpn.run -Algorithm SHA256
```

将计算结果写入本地 `.env`，同时确定本机 UDP 入口：

```ini
UNIVPN_SHA256=替换为安装程序的64位SHA256摘要
VPN_CONFIG_DIR=./private
WG_PORT=51829
```

安装包、`.env` 和 `private/` 都不提交到 Git。这里的 SHA256 固定本地构建输入，不代表任意厂商版本都兼容。

### 2. 填写网关、目标范围和真实探针

将 `examples/vpn.json` 复制为 `private/vpn.json`，例如：

```json
{
  "gateway": "vpn.example.com",
  "port": 443,
  "vpn_interface": "cnem_vnic",
  "allowed_cidrs": ["10.80.0.11/32"],
  "wireguard_client": "10.203.0.2/32",
  "probe": {
    "host": "10.80.0.11",
    "port": 22,
    "banner_prefix": "SSH-2.0-"
  }
}
```

`allowed_cidrs` 是允许转发的目标范围。先从确认需要的单机 `/32` 开始；网关实际下发了哪些路由，要连接后再核对。实验环境可能使用看起来像公网的地址，不能据此扩大成整个 `/8`。

这里使用 SSH banner 判断目标是否可达。**探针使用 SSH，不影响转发 HTTP 或 UDP。** `wireguard_client` 则是 Windows 接入端的地址，要与 WireGuard 配置一致，并避开现有局域网、Docker 和其他 VPN 的地址范围。

证书默认验证 CA 链和主机名。自签证书需要先独立核验，再按仓库文档设置明确批准的叶证书摘要。当前做法是独立 TLS 预检加本次登录例外，尚未将预检连接与引擎后续连接绑定，不能称为引擎侧证书 pinning。

### 3. 配对 Windows 与容器的 WireGuard

在本机分别生成容器端和 Windows 端密钥，将配置保存为 `private/wg0.conf`、`private/univpn-lab.conf`。可参考仓库的[容器端模板](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/examples/wg0.conf)和 [Windows 模板](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/examples/windows.conf)，生成命令见快速开始。

| 配置项 | 容器 `wg0.conf` | Windows `univpn-lab.conf` |
| --- | --- | --- |
| Interface Address | `10.203.0.1/30` | `10.203.0.2/32` |
| Interface PrivateKey | 容器自己的私钥 | Windows 自己的私钥 |
| Peer PublicKey | Windows 公钥 | 容器公钥 |
| Peer AllowedIPs | `10.203.0.2/32` | `10.80.0.11/32` |
| Peer Endpoint | 无需填写 | `127.0.0.1:51829` |
| ListenPort | `51820` | 无需固定 |
| MTU | `1280` | `1280` |
| Table | `off` | 不填写 |

两端各自保留私钥，只交换公钥。Windows 的 `AllowedIPs` 与 `vpn.json` 的目标 CIDR 一致；容器 peer 的 `AllowedIPs` 只接受 Windows 接入地址。`.env` 的 `WG_PORT` 对应 Windows Endpoint 的端口，容器内仍监听 `51820/udp`。

私钥文件只应允许自己、SYSTEM 和管理员读取。Git 忽略目录不能代替文件权限；按快速开始设置 Windows ACL，容器加载时会再将配置复制到权限为 `0600` 的运行目录。

两端配置在首次启动前准备好，服务会自动加载容器端的 `wg0.conf`。首次路径不需要再手工热加载。

### 4. 在终端完成账号密码和短信认证

```powershell
docker compose build
docker compose up -d
docker compose exec vpn vpnctl login
docker compose exec vpn vpnctl status
```

`login` 隐藏输入密码；网关要求短信时，在同一终端输入最新验证码。密码和验证码不写进 `.env`、命令参数或配置文件。交互登录需要 TTY，不加 `-T`。

如果要在收到短信挑战后先返回，再续交验证码：

```powershell
docker compose exec vpn vpnctl login --no-otp
docker compose exec vpn vpnctl sms
```

`sms` 继续现有挑战，不重新提交密码或重发短信。`--no-otp` 返回成功可能只表示正在等待验证码；只有 `status` 中 `data_plane_ready` 为 `true` 且退出码为 0，才表示真实目标探针通过。

过期、失败或取消后，先 `docker compose restart vpn`，再显式执行 `vpnctl login`。项目不自动重试密码或重发短信；也可以用 `vpnctl cancel` 取消当前等待中的认证。

<details>
<summary>已有已认证容器，后来才加入 WireGuard 时</summary>

如果容器启动前已有 `wg0.conf`，服务会自动加载。若刚完成短信登录后才新增配置，可以在尚无 `wg0` 时热加载，保留当前认证会话：

```powershell
docker compose exec vpn sh -c 'install -m 600 /config/wg0.conf /run/univpn/wg0.conf && wg-quick up /run/univpn/wg0.conf'
```

</details>

### 5. 安装一条独立的 Windows 隧道服务

[WireGuard 支持每条隧道独立运行 Windows 服务](https://git.zx2c4.com/wireguard-windows/about/docs/enterprise.md)，无需一直打开管理界面。仓库脚本默认只读，先检查配置和计划：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/windows-gateway.ps1 -TunnelConfig private/univpn-lab.conf -GatewayConfig private/vpn.json -Endpoint 127.0.0.1:51829
```

确认范围后安装；这一步创建系统服务、网卡和路由，需要管理员权限，`-Elevate` 会请求 UAC 确认：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/windows-gateway.ps1 -Mode Install -TunnelConfig private/univpn-lab.conf -GatewayConfig private/vpn.json -Endpoint 127.0.0.1:51829 -Elevate
```

配置名必须是独立的 `univpn-*.conf`。脚本检查官方 WireGuard 程序签名，拒绝覆盖已有同名服务或网卡，也拒绝默认路由、DNS 修改和配置 hooks。`ExecutionPolicy Bypass` 只作用于这次脚本进程。

相同目标可能已被另一套 VPN 下发路由。脚本只调整本次新建接口的 IPv4 ActiveStore metric，再逐个检查目标的最佳路由；不会改其他 VPN 的优先级。接口重建或系统重启后仍要复核，这部分持久性尚未验收。

### 6. 检查普通应用的实际路径

```powershell
Get-Service 'WireGuardTunnel$univpn-lab'
Find-NetRoute -RemoteIPAddress 10.80.0.11
& "$env:ProgramFiles\WireGuard\wg.exe" show univpn-lab
docker compose exec vpn ip route get 10.80.0.11
docker compose exec vpn vpnctl status
ssh your-user@10.80.0.11
```

最佳路由应选中新接口 `univpn-lab`，容器到目标应走 `cnem_vnic`，WireGuard 应有近期握手和增长的收发计数。然后在不绑定接口或源地址的情况下测试实际应用；服务显示 Running、接口 Up 或单独一次 SSH 成功，都不足以证明走了新链路。

目标有 HTTP 服务时，可以再执行下面的请求；端口以实际服务为准。`--noproxy` 用于排除应用代理，避免把代理连通误认成网关连通。

```powershell
curl.exe --noproxy "*" http://10.80.0.11:8080/
```

此后 WindTerm、浏览器等应用填写目标原始 IP 和服务端口即可，例如 SSH 的 `10.80.0.11:22`。应用自己配置的 HTTP/SOCKS 代理仍需另查；Windows 路由不会取消应用内的代理设置。

### 7. 停止和回滚只操作当前实例

移除本次 Windows 隧道，再停止对应容器：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/windows-gateway.ps1 -Mode Uninstall -TunnelConfig private/univpn-lab.conf -Elevate
docker compose stop vpn
```

卸载只针对这条命名隧道，不需要读取私钥，也不删除其他 VPN 路由。重新启动容器后需要显式登录。若旧 Windows VPN 仍在线，卸载后目标可能继续可达，应重新看最佳路由，不能拿“还能访问”证明当前实例没有停掉。

## 多实例：每套 VPN 独立配置和入口

第二套 VPN 使用另一个 Compose project；配置仍放在被忽略的 `private/` 内。两份本地 env 文件都填写安装包摘要，并分别设置 `VPN_CONFIG_DIR`、`WG_PORT`。

| 项目 | VPN A | VPN B |
| --- | --- | --- |
| Compose project | `vpn-a` | `vpn-b` |
| 配置目录 | `./private/a` | `./private/b` |
| 本机 UDP 端口 | `51829` | `51830` |
| Windows 接入地址 | `10.203.0.2/32` | `10.204.0.2/32` |
| Windows 隧道名 | `univpn-a` | `univpn-b` |
| 示例目标 | `10.80.0.11/32` | `10.90.0.11/32` |

```powershell
docker compose --env-file private/vpn-a.env -p vpn-a up -d
docker compose --env-file private/vpn-a.env -p vpn-a exec vpn vpnctl login
docker compose --env-file private/vpn-b.env -p vpn-b up -d
docker compose --env-file private/vpn-b.env -p vpn-b exec vpn vpnctl login
```

每个实例生成独立密钥，Windows 配置指向各自的 localhost UDP 端口。保留 Docker bridge 隔离，不使用 host 网络，也不共享两个 VPN 的网络命名空间。容器内接口都叫 `wg0`、`cnem_vnic` 没关系。

容器能隔离远端路由，但 Windows 只看到目的 IP。两套 VPN 的目标 CIDR 重叠时，当前方案不能同时区分，应另做地址映射或切换使用；也不能绕过网关对同一账号的并发限制。

## 简化取舍：保留必要的两段隧道

这套方案有两个必要部分：UniVPN 连接远端网关，WireGuard 把 Windows 流量送进对应容器。把 `wg0` 放在同一个 VPN 容器中后，共用现成的路由和防火墙规则，部署上只保留一个容器。

认证入口采用 `vpnctl` 和 Python 标准库，不再维护桌面、VNC 或额外 Web 登录服务。短信仍由用户输入，失败后显式重新登录，避免后台反复发短信或重试密码。后续可简化配置生成，但会话、证书和转发范围仍需要明确保存。[简化分析](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/docs/simplification.md)记录了这些取舍。

这次教程进一步合并了首次接入步骤：镜像只构建一次，两端 WireGuard 配置在首次启动前准备好，省去登录后的手工热加载。快速开始中的命令片段会生成配对密钥，并从 `vpn.json` 读取目标列表，减少重复填写。

下一步最值得做的是把这些片段收敛成**一个 profile 初始化命令**，由一份配置生成双端文件，再复用现有预检和安装脚本。这部分尚未实现。直接删除 WireGuard 不能靠一条指向 Docker bridge 的 Windows 路由补上三层入口；WSL 镜像网络也还没有验证出可替换的路径，因此当前先保留已验证的数据链路。

单个已连接的正式容器曾测得 **18.8 MiB 内存、CPU 1.26%**，这只是一次采样，不代表稳态或峰值。Compose 的 `384 MiB` 是上限，Docker Desktop / WSL 的平台开销要在 Windows 上另测；减少 VPN 进程并不能消除这部分开销。

## 实测结果与当前边界

2026-10-29 的 Windows 验收使用普通 TCP/UDP socket 和 HTTP 客户端，没有绑定接口、源地址或 HTTP/SOCKS 代理。除目标 IP 外，还交叉核对最佳路由、WireGuard 计数与远端看到的 VPN 来源。

| 验证项目 | 结果 |
| --- | --- |
| 无 GUI 的真实短信认证 | 同一引擎会话续交验证码，认证和隧道启动成功 |
| Windows 默认选路的 SSH | 4 台目标的 SSH banner，4/4 通过 |
| HTTP 下载、上传 | 双向各 1 MiB，长度与摘要匹配 |
| UDP 往返 | 32、1200、4096 字节内容均正确返回 |
| 临时阻断健康探针 | 转发切换为 DROP，SSH、HTTP、UDP 均失败 |
| 恢复健康探针 | 转发自动恢复，全部业务测试重新通过，无需新验证码 |

这次配置只包含 **4 个精确 `/32`**。测试路径中 UniVPN MTU 为 1300，WireGuard 使用 1280；大 UDP 内容经过分片并正常返回，只能证明本次路径可用。临时 HTTP/UDP 测试服务已清理。

探针故障测试没有断开厂商 VPN 会话，不能代替真实断线、重新认证和 Docker 重启恢复。Windows 服务或系统重启后的路由优先级、条件 DNS、IPv6，以及重叠 CIDR 访问也都还没有完成验收。

另一个需要区分的状态是：并发状态查询曾干扰后台健康检查，源码已经修复为“后台独占探测、状态只读最近结果”，回归测试通过。**当前保持连接的旧容器尚未更换镜像，这项修复还未在该会话生效。** 维护部署需要重建并重新认证，不能把源码修复写成线上已经生效。

详细方法和结果放在[网段网关验证记录](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/docs/subnet-gateway-validation.md)，后续仍按认证、容器转发、Windows 选路和实际业务分别验收。

## 旧方案保留为历史参考

最初参考 [jesusdf/huawei-vpn](https://github.com/jesusdf/huawei-vpn)，用 expect 驱动厂商 CLI，再用 socat 暴露几个本地 SSH 端口。它适用于当时验证过的账号密码入口，但旧菜单在本次短信环境没有续交验证码的流程。

后续通过官方引擎的 CSDK/RPC 路径完成了纯终端短信认证，再用 WireGuard 接入 Windows。旧方案的[认证对照记录](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/docs/cli-mfa-proof.md)仍保留，本文的操作步骤以当前 native 网关路线为准。
