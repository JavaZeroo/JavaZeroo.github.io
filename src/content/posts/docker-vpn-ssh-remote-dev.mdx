Windows 的 UniVPN 客户端一次只能连接一套环境。我需要保留原来的 VPN，同时访问另一套内网，又不想多开一台 Windows 虚拟机，于是把额外的 UniVPN 放进 Docker。

现在的结构是：**每套 UniVPN 独占一个容器，Windows 通过 WireGuard 把指定目标的流量送进去。** 配好后，WindTerm、浏览器和其他应用直接填写原始内网 IP 与端口，无需逐个映射 SSH 入口。

使用入口也收敛成了两条命令：从预构建镜像导出 Windows 启动器，然后运行它。配套项目是 [JavaZeroo/univpn-docker-gateway](https://github.com/JavaZeroo/univpn-docker-gateway)，镜像位于 [Docker Hub](https://hub.docker.com/r/javazero/univpn-docker-gateway)。本文对应 `0.2.0` 的使用方式；原数据链已有真实短信和 Windows 多协议证据，新启动器的完整接入流程仍需单独验收。

## Windows 通过 WireGuard 接入独立的 UniVPN 容器

容器拥有独立的网络命名空间。UniVPN 创建的 `cnem_vnic`、内网路由和转发规则留在对应容器中。增加一套 VPN，就增加一个独立实例，分别使用密钥、接入地址和 UDP 端口。

Windows 还需要到容器的网络入口。[Docker Desktop 的 Linux 容器网络位于虚拟机内部](https://docs.docker.com/desktop/features/networking/networking-how-tos/)，不能直接把容器 IP 当作 Windows 路由的下一跳。这里通过发布到 `127.0.0.1` 的 UDP 端口接入 WireGuard。

<UniVpnArchitecture />

图中的**数据面**承载业务：Windows 应用 → Windows WireGuard → localhost UDP → 容器 `wg0` → 转发与 SNAT → `cnem_vnic` → 内网。SNAT 将来源换成容器的 VPN 地址，让远端回包沿原路返回。

**控制面**负责登录和决定何时允许转发。启动器调用容器内的 `vpnctl`，在终端收取账号、密码和短信验证码，再由 Python 服务通过 CSDK/RPC 控制官方 UniVPNCS。验证码续交到原引擎、原登录会话。

后台守卫检查 VPN 接口、目标路由和真实业务探针。探针失败后，专属转发链切换为 DROP；正常流量还必须从 `wg0` 转向指定 VPN 接口，不能改从容器普通出口发走。状态更新有轮询与探针超时延迟。

WireGuard 只连接 Windows 与本机容器，远端仍由 UniVPN 连接。容器内 `wg0` 是 Linux 内核接口，**不需要额外的 WireGuard 常驻进程或辅助容器**。[WireGuard 网络命名空间说明](https://www.wireguard.com/netns/)介绍了这层关系。

## 预构建镜像与按需获取的厂商引擎分开

主机只需 Docker Desktop 的 Linux 容器环境和 [WireGuard for Windows](https://www.wireguard.com/install/)。用户不需要 Git、本机 Python、手工生成密钥或本地构建镜像。

<UniVpnDependencies />

| 层次 | 组件与职责 |
| --- | --- |
| Windows | WireGuard 提供网卡；导出的 cmd / PowerShell 启动器生成配置、连接、检查状态和移除本实例入口 |
| Docker Desktop / WSL2 | 提供 Linux 容器、独立网络命名空间、内核 WireGuard、TUN 和 localhost UDP 发布 |
| 公开镜像 | Ubuntu 22.04 amd64、tini、Python 标准库、iproute2、iptables、wireguard-tools 与 CA |
| 首次获取的厂商组件 | UniVPNCS、辅助服务及运行库，负责远端认证与隧道；固定版本 **10781.21.0.0831** |

`Dockerfile.public` 不包含厂商二进制。首次启动时从官方获取固定版本，依次校验 ZIP、内嵌 run 文件和六个运行文件的 SHA256，只提取允许的文件，**不执行安装脚本**。校验后的组件保存到具名 `vendor-cache` 卷，后续复用缓存；失败时不使用未校验文件。具体来源与摘要见[镜像说明](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/docs/image-release.md)。

容器使用 bridge 网络，额外授予 `NET_ADMIN` 和 `/dev/net/tun`，不使用 privileged 或 host 网络。默认路径没有 Qt、X11、Xvfb、DBus、VNC，也没有额外 Python 第三方依赖。厂商程序仍遵循自身许可，项目自写代码采用 GPL-3.0-only。[架构文档](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/docs/architecture.md)记录了组件边界。

## 首次连接只保留导出和运行两步

先安装 Docker Desktop 和 WireGuard for Windows，并启动 Docker Desktop。在保存配置的目录打开 PowerShell：

```powershell
docker run --rm -v "${PWD}:/output" javazero/univpn-docker-gateway:latest export-client
.\univpn\univpn.cmd
```

第一条将四个客户端文件导出到 `univpn/`：`univpn.cmd`、主 PowerShell 启动器、profile 生成器和 Windows 网关安装器。**导出不会覆盖已有目录**；以后直接运行第二条命令。cmd 只为本次 PowerShell 进程设置执行策略，不修改持久策略。

按提示填写：

- **网关**：支持 `vpn.example.com:443` 这样的 `host:port`。
- **目标 CIDR**：例如 `10.80.0.11/32`，只填确认需要的范围，不扩大成整个 `/8`。
- **SSH 探针**：选择一个实际可达的目标，用于判断 VPN 是否能承载业务。探针使用 SSH，转发仍支持 HTTP 和 UDP。

启动器生成配对密钥、受限 ACL、JSON 和 Compose 配置，然后拉取并启动镜像，等待厂商组件与控制服务就绪，再在 TTY 中执行登录或短信续交。账号、密码和验证码不写配置；私钥留在本地受限文件中。

容器探针通过后，启动器复用或安装独立命名的 `univpn-*` WireGuard 网卡。首次安装需要用户确认 UAC；它只调整本次新网卡的 IPv4 ActiveStore 优先级，不修改其他 VPN。最后用 Windows 普通连接检查真实目标 banner，不能仅凭认证成功或网卡 Up 就宣布连通。

连接后直接使用原始 IP：

```powershell
ssh your-user@10.80.0.11
curl.exe --noproxy "*" http://10.80.0.11:8080/
```

端口以目标实际服务为准。`--noproxy` 排除应用代理；应用自己设置的 HTTP/SOCKS 代理不会被 Windows 路由取消。证书默认验证 CA 链和主机名，自签证书需独立核验后配置明确批准的摘要；独立 TLS 预检不等于引擎侧连接 pinning。细节见[快速开始](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/docs/quickstart.md)。

## 日常启停只操作当前 profile

```powershell
.\univpn\univpn.cmd                   # 连接；有有效短信挑战时续交
.\univpn\univpn.cmd -Mode Status      # 状态和最佳路由
.\univpn\univpn.cmd -Mode Stop        # 停容器，保留网卡、密钥与缓存
.\univpn\univpn.cmd -Mode Remove      # 卸载本实例网卡并移除容器
```

`Stop` 保留 Windows 入口，所以目标可能仍指向已停止的容器；需要释放该入口时用 `Remove`。`Remove` 执行本实例的 WireGuard 卸载与 Compose down，**不删除密钥文件或下载缓存**，也不移除其他 VPN。

短信过期或失败后，不自动重发；显式 Stop 后重新连接。有有效挑战时只续交验证码，不重复登录。若旧 VPN 仍在线，移除新网卡后可能恢复接管同一目标，这属于回退，需要通过最佳路由区分。

## 第二套 VPN 只换实例参数

新实例使用不同的名称、UDP 端口和接入网段：

```powershell
.\univpn\univpn.cmd -Name work -UdpPort 51830 -AccessSubnet 10.204.0.0/30
```

这些值会保存在该 profile 中，以后加 `-Name work` 即可，例如 `-Name work -Mode Status`。每个实例生成独立密钥，配置放在 `univpn/private/<名称>/`，容器中的接口可以同样叫 `wg0`、`cnem_vnic`。接入网段还需避开现有局域网、其他 VPN 和 Docker 网络。

容器能隔离远端路由，但 Windows 按目的 IP 选路。两套 VPN 的目标 CIDR 重叠时，当前不能同时区分，仍需地址映射或切换使用；也不能绕过网关的账号并发限制。

## 简化的是配置操作，保留两段隧道

以前需要手工维护网关 JSON、两端 WireGuard 配置、密钥权限、Compose 和服务安装命令。现在由一份 profile 生成这些文件，目标 CIDR 只输入一次；连接、状态、停止和移除也使用同一个入口。

预构建镜像省去了用户本机构建，厂商组件的固定获取、逐层校验和缓存则留在运行准备阶段。UniVPN 仍负责远端网关，WireGuard 仍负责 Windows 到容器；直接删除 WireGuard，不能靠一条指向 Docker bridge 的静态路由补上这段入口。

会话、证书和目标白名单仍明确保存，短信仍由用户输入。这些约束没有因启动器变短而消失。Docker Desktop/WSL2 的平台开销也需要单独测量，镜像免构建不代表没有内存成本。[简化分析](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/docs/simplification.md)说明了取舍。

## 原数据链的实测与新启动器的验收分开

2026-10-29 的 Windows 验收使用普通 TCP/UDP socket 和 HTTP 客户端，没有绑定接口、源地址或 HTTP/SOCKS 代理，并交叉核对最佳路由、WireGuard 计数与远端 VPN 来源。

| 验证项目 | 结果 |
| --- | --- |
| 无 GUI 的真实短信认证 | 同一引擎会话续交验证码，认证和隧道启动成功 |
| Windows 默认选路的 SSH | 4 台目标的 SSH banner，4/4 通过 |
| HTTP 下载、上传 | 双向各 1 MiB，长度与摘要匹配 |
| UDP 往返 | 32、1200、4096 字节内容均正确返回 |
| 临时阻断 / 恢复健康探针 | SSH、HTTP、UDP 全部阻断，恢复后再次通过，无需新验证码 |
| 新启动器的配置与完整接入 | 镜像导出的 CMD 已实际生成密钥与 Compose 并通过只读预检；完整短信及 Windows 安装尚未验收 |
| 公开镜像准备 | 冷缓存官方下载、无网络新容器复用缓存，以及隔离官方引擎启动均通过 |

原数据链只配置 **4 个精确 `/32`**，UniVPN MTU 为 1300，WireGuard 使用 1280；大 UDP 内容分片后正常往返，只能证明本次路径可用。探针故障没有断开厂商 VPN 会话，不能替代真实断线、重新认证和 Docker 重启恢复。DNS、IPv6、重叠 CIDR 以及服务重建后的路由优先级仍未完整验收。

状态缓存修复已合入源码并有回归测试；当前保持连接的旧容器没有重启，不能将源码修复写成这个旧会话已经应用。新镜像与新启动器的验证也不复用旧会话的成功结论。[完整实测记录](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/docs/subnet-gateway-validation.md)按各层分别记录证据。
