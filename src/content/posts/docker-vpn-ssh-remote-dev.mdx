Windows 的 UniVPN 客户端一次只能连接一套环境。我需要保留原来的 VPN，同时访问另一套内网，又不想多开一台 Windows 虚拟机，于是把额外的 UniVPN 放进 Docker。

**每套 UniVPN 独占一个容器，接入方式分成 Lite 和 Full 两版。** Lite 只运行 Docker，把 VPN 提供为应用的 SOCKS5 代理；Full 通过 Windows WireGuard 网卡接入，应用直接填写原始内网 IP 与端口。

配套项目是 [JavaZeroo/univpn-docker-gateway](https://github.com/JavaZeroo/univpn-docker-gateway)，预构建镜像位于 [Docker Hub](https://hub.docker.com/r/javazero/univpn-docker-gateway)。本文对应 `0.4.0`：`lite` / `0.4.0-lite` 是代理版，`full` / `0.4.0-full` 是原始 IP 接入版；`latest` 和 `0.4.0` 继续指向 Full。

| 需求 | 选择 |
| --- | --- |
| 不安装 Windows VPN 网卡，应用可以配置 SOCKS5，只需要 IPv4 TCP | Lite |
| 直接用原始 IP，需要 UDP，或不想逐个配置应用代理 | Full |

## 架构设计总览：两种入口接入独立容器

两版的远端连接都由官方 UniVPN 引擎负责。区别在本机到容器这一段：Lite 发布 localhost TCP 代理端口，Full 发布 localhost UDP 端口并连接 Windows WireGuard 网卡。

## Lite 在容器终端启动并提供 SOCKS5 代理

先启动 Windows x64 的 Docker Desktop，使用 Linux 容器 / WSL2。在 PowerShell 执行：

```powershell
docker run --rm -it --log-driver none --name univpn-lite `
  --cap-add NET_ADMIN --device /dev/net/tun `
  -p 127.0.0.1:1080:1080 `
  -v univpn-lite-config:/config `
  -v univpn-vendor-cache:/var/cache/univpn `
  javazero/univpn-docker-gateway:lite
```

首次在容器终端填写网关 `host:port`、允许访问的 IPv4 CIDR，以及其中一台 SSH 探针的 `IP:port`。例如只访问 `10.80.0.11/32` 时，可默认使用该地址的 22 端口。网络配置保存到具名卷里的 `/config/lite/vpn.json`，不用准备本机 JSON 文件。

随后在同一终端输入 VPN 账号、密码与本次短信。连接后保持终端运行，`Ctrl+C` 停止；网络配置和已验证的厂商缓存会保留，凭据不写配置，也不会自动重发短信。

应用的代理类型选择 **SOCKS5**，地址填 `127.0.0.1`，端口填 `1080`。例如：

```powershell
curl.exe --proxy socks5h://127.0.0.1:1080 http://10.80.0.11:8080/
```

这里只支持数字 IPv4，`socks5h` 不代表代理能解析真正的目标域名。SSH 需要使用支持 SOCKS5 的客户端并配置会话代理；直接执行 `ssh user@10.80.0.11` 不会自动通过 Lite。

Lite 使用 Python 标准库实现 **SOCKS5 CONNECT-only / IPv4 TCP**，不支持 UDP ASSOCIATE、BIND、IPv6 或域名 DNS。规范的数字 IPv4 即使放在 SOCKS5 的域名字段中，也可以使用。代理仅允许配置的目标 CIDR，不能把它当作通用公网代理。[Lite 使用说明](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/docs/lite.md)记录了完整范围。

## Full 两条命令准备 Windows 网卡，按原始 IP 访问

Full 同样只需预装 Docker Desktop。在 Windows 新建空文件夹，在该文件夹打开 PowerShell：

```powershell
docker run --rm -v "${PWD}:/output" javazero/univpn-docker-gateway:full export-client
.\univpn\univpn.cmd
```

第一条把 Windows 启动器导出到当前文件夹的 `univpn/` 子目录。第二条在同一个 PowerShell 窗口运行它；`.\` 表示当前目录。启动器按需准备官方 WireGuard、生成配置和配对密钥，再启动容器，收取登录信息并续交短信。

已有签名有效的 WireGuard 安装会复用，不升级或重装。首次安装 Windows 程序与创建专属 `univpn-*` 隧道可能分别需要 UAC；若安装器要求重启，启动器会停止流程并告知用户。执行策略例外只限本次 PowerShell 进程。

填写网关、精确目标 CIDR 和 SSH 探针后，容器先完成认证、隧道与真实探针检查，再安装或核验 Windows 网卡。最后由 Windows 普通连接检查目标 SSH banner。连接后可以直接使用：

```powershell
ssh your-user@10.80.0.11
curl.exe --noproxy "*" http://10.80.0.11:8080/
```

`--noproxy` 排除应用代理，目标端口以实际服务为准。Full 通过目标路由承载 TCP / UDP；探针使用 SSH，不代表转发只支持 SSH。WireGuard 位于宿主机的 `C:\Program Files\WireGuard`，容器中的 `wireguard-tools` 不能代替 Windows 网卡。

启动器不修改旧 tunnel 配置，但目标 CIDR 重叠仍可能改变 Windows 实际选路，需要核对。不能把独立名称理解成所有流量都互不影响。[Full 快速开始](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/docs/quickstart.md)包含首次使用细节。

## 两版的数据面不同，认证和真实就绪判断共用

容器拥有独立网络命名空间，UniVPN 创建的 `cnem_vnic`、路由与过滤规则留在对应实例。Docker Desktop 的 Linux 容器位于虚拟机内部，[不能直接把容器 IP 当作 Windows 路由下一跳](https://docs.docker.com/desktop/features/networking/networking-how-tos/)，所以需要代理端口或 WireGuard 入口。

<UniVpnArchitecture />

Lite 的业务连接经过 Python SOCKS5 服务。它检查目标 CIDR、真实就绪状态和目标路由，并把出站 socket 绑定到 `cnem_vnic`。VPN 不可用时关闭代理流量，不能改从 `eth0` 发出。

Full 的业务包经过 `wg0`、iptables FORWARD 与 SNAT，不经 Python 用户态代理。SNAT 将来源换成容器的 VPN 地址，让回包沿原路返回。专属转发链只允许配置的目标和 VPN 出口；后台探针失败后切换为 DROP。

两版都由终端前端调用 `vpnctl`，Python 服务再通过 CSDK/RPC 控制官方 UniVPNCS。验证码续交到原引擎、原认证会话。守卫检查认证、接口、路由和真实 SSH 响应，状态查询读取缓存；轮询和探针超时会带来检测延迟。认证成功、容器 Up 或端口存在，都不能代替数据面验证。

证书默认验证 CA 链和主机名。自签证书需要事先独立核实叶证书 SHA256，再显式批准；独立 TLS 预检不等于引擎侧连接 pinning。密码、短信不保存到参数、环境变量或配置中，也不使用桌面自动化登录。

## 依赖分为共同部分与版本专用部分

用户不需要 Git、本机 Python、手工生成密钥或本地构建。两版都依赖 Docker Desktop / WSL2、Python 标准库和官方引擎；WireGuard 仅属于 Full。

<UniVpnDependencies />

| 共同依赖 | Lite 额外部分 | Full 额外部分 |
| --- | --- | --- |
| Ubuntu 22.04 amd64、Python 标准库、tini、iproute2、iptables、CA、TUN | Python SOCKS5 服务，配置保存于 Docker 卷 | Windows WireGuard 与启动器；容器 wireguard-tools 和内核 wg0 |
| 原生认证控制器、官方 UniVPNCS 与辅助组件 | 发布 localhost TCP 代理端口 | 发布 localhost UDP，生成配对配置与专属 Windows 服务 |

`Dockerfile.public` 不包含厂商二进制。首次从官方获取固定 **10781.21.0.0831**，依次校验 ZIP、内嵌 run 文件及六个运行文件的 SHA256，只提取白名单文件，**不执行安装脚本**。具名卷保存已验证的 ZIP 缓存，各容器加载自己的运行副本；失败不使用未校验文件。[镜像说明](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/docs/image-release.md)记录了固定来源与摘要。

容器使用 bridge 网络、`NET_ADMIN` 与 `/dev/net/tun`，不使用 privileged 或 host 网络。两版都没有 Qt、X11、Xvfb、DBus、VNC 或额外 Python 第三方依赖；Lite 也没有 `wireguard-tools` 和 Windows 脚本。厂商程序遵循自身许可，项目自写代码采用 GPL-3.0-only。

## 多实例分别选择代理端口或接入网段

Lite 新增一套 VPN 时，更换容器名、配置卷和本机发布端口，例如将 `univpn-lite`、`univpn-lite-config`、`127.0.0.1:1080:1080` 改成 `univpn-work`、`univpn-work-config`、`127.0.0.1:1081:1080`。应用选择对应的 SOCKS5 端口，就选择了对应 VPN；厂商缓存卷可以复用。

Full 新增一套 VPN 时，使用不同名称、UDP 端口和接入网段：

```powershell
.\univpn\univpn.cmd -Name work -UdpPort 51830 -AccessSubnet 10.204.0.0/30
```

以后加 `-Name work` 即可操作这个 profile。接入网段需避开局域网、其他 VPN 和 Docker 网络。Windows 按目的 IP 选路，Full 不能同时区分两套 VPN 中相同的目标地址；Lite 可以由不同应用选择各自代理，但也不能绕过网关的账号并发限制。

## 两版的停止方式与短信续交命令

Lite 前台 `Ctrl+C` 停止，`--rm` 移除本次容器，配置和缓存卷仍保留。运行期间可在另一终端检查：

```powershell
docker exec univpn-lite vpnctl status
docker exec -it univpn-lite vpnctl sms
```

`sms` 只续交尚未过期的现有挑战。失败、过期或取消后，停止当前容器，再显式执行启动命令发起新尝试。

Full 使用同一个 Windows 入口：

```powershell
.\univpn\univpn.cmd                   # 连接；有效短信挑战会续交
.\univpn\univpn.cmd -Mode Status      # 状态和最佳路由
.\univpn\univpn.cmd -Mode Stop        # 停容器，保留网卡、密钥和缓存
.\univpn\univpn.cmd -Mode Remove      # 移除本实例网卡与容器，保留文件和缓存
```

Full 的 `Stop` 保留 Windows 路由，目标可能继续指向已停止的入口；需释放入口时用 `Remove`。删除新网卡后，旧 VPN 可能重新接管重叠目标，需要用最佳路由区分回退。两版都不自动重新登录或重发短信。

## 已有 Full 链路实测与新增 Lite 入口分别验收

2026-10-29 的原数据链验收使用 Windows 普通 TCP / UDP socket 和 HTTP 客户端，没有绑定接口、源地址或应用代理，并交叉核对最佳路由、WireGuard 计数与远端 VPN 来源。

| 验证范围 | 证据与边界 |
| --- | --- |
| 共用原生认证路径 | 无 GUI 的真实短信续交成功，同一引擎会话完成认证与隧道启动 |
| Full 原始 IP 数据链 | 4/4 SSH banner；双向各 1 MiB HTTP 长度与摘要匹配；32、1200、4096 字节 UDP 正确往返 |
| Full 探针故障与恢复 | SSH、HTTP、UDP 全部阻断，恢复后再次通过，原认证保留 |
| Full 宿主机准备与启动器 | 一次性 Windows CI 实装 WireGuard 通过，本机复用既有安装；配置、密钥和只读预检通过，完整新用户接入仍需单独验收 |
| 公开镜像组件准备 | 官方冷缓存下载、无网络新容器复用缓存，以及隔离官方引擎启动通过 |
| Lite 新 SOCKS5 入口 | 不能沿用 Full 数据链结论；仍待真实 VPN 登录后的端到端验收 |

原 Full 数据链使用 **4 个精确 `/32`**，UniVPN MTU 为 1300，WireGuard 为 1280；大 UDP 分片往返只能证明当次路径可用。探针故障没有断开厂商 VPN 会话，不能替代真实断线、重新认证或 Docker 重启恢复。DNS、IPv6、服务重建后的路由优先级也未完整验收；Lite 明确不提供 UDP 和目标域名解析。[完整实测记录](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/docs/subnet-gateway-validation.md)按各层记录证据。

Lite 省去了 Windows 网卡和 WireGuard，Full 则保留原始 IP 接入；Docker Desktop / WSL2 的平台开销都还存在。镜像大小、单容器内存和整个平台占用应分别测量，不能把一次容器样本当作整机资源承诺。
