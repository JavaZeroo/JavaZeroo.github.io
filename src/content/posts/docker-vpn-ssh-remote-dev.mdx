我用的 Windows UniVPN 客户端一次只能连接一套 VPN。需要同时访问另一套内网时，又不想额外开一台 Windows 虚拟机，于是把另一套 UniVPN 放进 Docker Desktop 的 Linux 容器。

**一套 VPN 一个容器，各自维护网卡和路由。** Windows 原有的 VPN 可以继续使用；还需要更多连接，就增加容器，用不同本地端口区分入口。

> 2026-10-27 更新：前半部分保留已经使用过的账号密码登录与 SSH 转发方案。后续已用独立 Python 终端前端连接官方引擎，完成无图形界面的短信认证、隧道启动和 4 台服务器 SSH 验证；正式容器单次内存样本为 18.8 MiB。文末补充新后端的用法，Windows 按网段接入的整条链路仍待实测。

## 为什么能共存

普通 bridge 网络下，每个容器都有自己的网络命名空间。UniVPN 创建的 `cnem_vnic` 网卡和下发的内网路由留在对应容器里，因此两个容器可以使用同样的网卡名，内网 IP 重复也能按入口区分。

不同 VPN 实例不要使用 `--network=host` 或共享彼此的网络命名空间，否则会失去这层隔离。同一套 VPN 的业务容器或网关辅助容器，可以有意共享它的网络命名空间。[Docker 的 host 网络说明](https://docs.docker.com/engine/network/drivers/host/)解释了共享网络命名空间的行为。

## 准备镜像

前提是 Docker Desktop 已切换到 Linux 容器，且 Linux UniVPN 客户端适配自己的网关。下面使用第三方项目 [jesusdf/huawei-vpn](https://github.com/jesusdf/huawei-vpn) 封装的命令行客户端，**镜像不是厂商官方发布的**。这套示例只验证了账号密码认证，不能直接用于本文遇到的短信认证环境，具体限制见文末。

在一个空目录中新建 `Dockerfile`：

```dockerfile
FROM jesusdf/huawei-vpn@sha256:f3d98c6229071a2b14d1907a393ecac7743ad1b4d7cc96f38875290d574cd45b

RUN apt-get update \
    && apt-get install -y --no-install-recommends socat \
    && rm -rf /var/lib/apt/lists/* \
    && sed -i 's/-re "Connect Success"/-nocase -re "connect success"/; /^spawn /i log_user 0' /opt/univpn/connect.exp

ENV USER=root
COPY vpn-forward.sh /vpn-forward.sh
ENTRYPOINT ["/bin/sh", "/vpn-forward.sh"]
```

这里固定镜像摘要，并兼容登录成功提示的大小写；同时关闭交互回显，避免账号密码被客户端回显进日志。

再新建 `vpn-forward.sh`，保存为 **LF 换行**：

```sh
#!/bin/sh
set -eu
: "${FORWARD_TARGET:?请设置内网目标 IP}"

socat TCP4-LISTEN:2222,bind=0.0.0.0,reuseaddr,fork \
  "TCP4:${FORWARD_TARGET}:${FORWARD_PORT:-22},connect-timeout=10" &

exec /bin/sh /entrypoint.sh
```

`socat` 在容器内监听 `2222`，收到连接后，再沿容器里的 VPN 路由连接目标服务器。它只是转发 TCP，SSH 仍由目标服务器验证身份。

构建镜像，以下单行命令可直接在 PowerShell 中运行：

```powershell
docker build -t univpn-forward:local .
```

## 启动两套 UniVPN

新建 `vpn-a.env`，填入第一套 VPN 的信息。以下全部为示例，需要替换：

```ini
VPN_GATEWAY=vpn-a.example.com
VPN_PORT=443
VPN_USERNAME=your-user-a
VPN_PASSWORD=replace-with-your-password
FORWARD_TARGET=10.80.0.11
FORWARD_PORT=22
```

复制为 `vpn-b.env`，填写第二套的网关、端口、账号、密码和内网目标。两套 VPN 的 `FORWARD_TARGET` 可以相同，因为它们分别通过自己的隧道访问。网关端口按实际配置填写，不一定是 `443`。

这两个文件包含密码，只保存在本机，不提交到 Git。环境变量也能被有 Docker 管理权限的人查看。

```powershell
docker run -d --name univpn-a --restart=no --cap-add=NET_ADMIN --device=/dev/net/tun --env-file vpn-a.env -p 127.0.0.1:22221:2222 univpn-forward:local
docker run -d --name univpn-b --restart=no --cap-add=NET_ADMIN --device=/dev/net/tun --env-file vpn-b.env -p 127.0.0.1:22222:2222 univpn-forward:local
```

`NET_ADMIN` 和 `/dev/net/tun` 用于建立 VPN 网卡。两条命令都使用默认 bridge 网络，容器名、认证文件和宿主机端口分别独立。这里把入口绑定到 `127.0.0.1`，供本机使用；端口映射规则见 [Docker 文档](https://docs.docker.com/engine/network/port-publishing/)。

如果 Windows 已经连接第一套 VPN，只启动额外需要的那一个容器即可，不必把两套都迁进去。容器隔离也不能绕过 VPN 服务端的账号并发限制，同账号能否多端在线仍取决于网关策略。

## Windows 应用怎么访问

SSH 工具直接填写对应入口：

| 环境 | 地址 | 端口 | 登录身份 |
| --- | --- | --- | --- |
| VPN A 内的服务器 | `127.0.0.1` | `22221` | 目标服务器的账号或密钥 |
| VPN B 内的服务器 | `127.0.0.1` | `22222` | 目标服务器的账号或密钥 |

这一步用的是**内网服务器的 SSH 账号**，与 VPN 登录账号是两回事。也可以在 Windows 的 `~/.ssh/config` 中写两个别名：

```ssh-config
Host vpn-a-node
  HostName 127.0.0.1
  Port 22221
  User dev
  HostKeyAlias vpn-a-node

Host vpn-b-node
  HostName 127.0.0.1
  Port 22222
  User dev
  HostKeyAlias vpn-b-node
```

之后执行 `ssh vpn-a-node` 或 `ssh vpn-b-node`。VS Code Remote SSH、SFTP 等工具也能使用对应入口。第一次连接时核对目标主机指纹。

这个例子只转发一个 TCP 服务。需要数据库等其他端口，可以增加对应的 `socat` 监听和 Docker 端口映射。需要让浏览器按代理访问更多内网地址，则应另配 SOCKS/HTTP 代理；仅启动 UniVPN 容器不会自动提供这种代理服务。

## 日常启停和排查

```powershell
docker logs --tail 30 univpn-a
docker exec univpn-a ip addr show cnem_vnic
docker exec univpn-a ip route get 10.80.0.11

docker stop univpn-a univpn-b
docker start univpn-a univpn-b
```

先确认登录成功、网卡存在，再看目标 IP 是否走 VPN 路由，最后测试本地 SSH 入口。端口已经监听不代表 VPN 已连通。如果提示密码错误，先停止容器再核对认证信息；基础镜像内部有重连逻辑，`--restart=no` 只控制 Docker 的重启策略。

不使用时停止容器。需要限制单个 VPN 容器资源时，可以在创建命令中加 `--memory=256m --cpus=0.5`，再观察实际占用调整；这个限制不包含 Docker Desktop 和 WSL 本身的开销。

## 短信认证：通过官方引擎保留纯终端交互

项目的 [connect.exp](https://github.com/jesusdf/huawei-vpn/blob/main/univpn/connect.exp) 驱动厂商命令行程序，依次提交账号、密码，然后等待连接结果，没有验证码输入分支。厂商安装包附带的《终端用户接入指南》10.2.2 更明确写出：Linux CLI 的 SSL VPN 连接仅支持用户名/密码认证。在后续测试的网关上，命令行客户端返回需要动态口令，原镜像无法完成认证。只给脚本增加一个验证码环境变量，不能补出厂商 CLI 没有提供的交互能力。

随后验证了官方引擎的另一条本地控制路径：**保留 UniVPNCS 负责认证和隧道，由独立 Python 前端通过 CSDK/RPC 接口完成终端交互。** 密码触发短信后，验证码续交到原引擎、原登录会话，不需要启动 GUI 或桌面。

配套项目 [JavaZeroo/univpn-docker-gateway](https://github.com/JavaZeroo/univpn-docker-gateway) 的默认 Compose 已使用这个后端。官方 10781.21.0.0831 的正式容器实测通过真实短信认证、TUN 隧道启动和 **4/4 台服务器的 SSH banner**。容器中只有 tini、Python、官方辅助服务和 UniVPNCS，Qt/Xvfb/DBus/AT-SPI/VNC 包检查为空。

按仓库说明取得厂商安装包、校验摘要并填写本地配置后运行：

```powershell
docker compose build
docker compose up -d
docker compose exec vpn vpnctl login
docker compose exec vpn vpnctl status
```

`login` 在当前终端输入账号密码，并等待最新短信验证码。也可以先用 `login --no-otp` 返回，随后运行 `docker compose exec vpn vpnctl sms` 续交。只有真实目标探针通过，`status` 才返回 `data_plane_ready: true` 并以状态码 0 退出；认证成功或网卡存在都不够。

连接后的单次 `docker stats` 样本为 **18.8 MiB / 384 MiB、CPU 1.26%**，不包含 Docker Desktop/WSL 固定开销，也不是稳态或峰值保证。验证码过期或认证失败后，需要 `docker compose restart vpn`，再显式运行 `vpnctl login`；没有自动重试密码或重复发送短信。协议和证书策略的限制见仓库[实测记录](https://github.com/JavaZeroo/univpn-docker-gateway/blob/main/docs/native-rpc-research.md)。

## 从 SSH 入口升级为网段网关

本地 SSH 端口只是第一阶段。更完整的目标是让 Windows 应用直接访问内网原始 IP，SSH、网页、数据库和 UDP 服务共用一套网段规则，无需为每个服务增加端口映射。

这里需要区分两个问题：容器内 UniVPN 已经是 VPN 客户端；缺少的是 **Windows 到这个容器的三层网络入口**。[Docker Desktop 文档](https://docs.docker.com/desktop/features/networking/networking-how-tos/)说明 Linux 容器网络位于虚拟机内部，Windows 不能直接访问每个容器 IP，因此不能简单地把 Docker 容器地址填成 Windows 的静态路由下一跳。

计划采用下面的结构，**尚未完成部署和端到端验证**：

```text
Windows 应用：直接访问内网 IP
    ↓ 只匹配配置的目标网段
Windows WireGuard 接口
    ↓ 本机发布的 UDP 端口
Docker 内的 WireGuard 接口
    ↓ 转发规则 + 源地址转换
同一网络命名空间内的 UniVPN 接口
    ↓
目标内网
```

WireGuard 是本机到容器的接入链路，远端仍使用原 UniVPN 协议。[WireGuard 支持网络命名空间](https://www.wireguard.com/netns/)，适合作为这个入口。可以让辅助容器共享**对应那一套** UniVPN 的网络命名空间；其他 VPN 实例仍保持独立。

每套 VPN 配置独立的接入地址、密钥、UDP 端口和目标网段。Windows 的 `AllowedIPs` 只包含确认需要的网段；容器启用 IP 转发，只允许这些目标从 WireGuard 转发到 UniVPN，并在 UniVPN 出口执行源地址转换，让回包能返回 Windows。未允许的目标，以及 VPN 断开后的转发，都应被拒绝，不能落到容器普通互联网出口。

配置时还需要解决几个实际问题：

- **路由冲突**：与 Windows 原生 VPN、Mihomo TUN 和本地局域网核对。多个 VPN 的目标网段重叠时，仅靠目的 IP 不能同时区分，应使用地址映射或分开使用环境。
- **网段范围**：优先录入实际下发且确实需要的前缀，必要时先用单机 `/32`。实验内网可能使用公网地址，不能凭 IP 外观扩大成整个 `/8`。
- **域名和数据包大小**：内网域名需要单独设计按域名分流的 DNS；双层隧道需要验证 MTU，避免小请求成功、大文件卡住。
- **健康检查**：WireGuard 握手、VPN 网卡存在都不代表目标可达。需要真实 SSH 握手、HTTP/UDP 请求，并测试断线、重连和 Docker 重启后的恢复。

这项改造应在新测试实例上先验证，保留现有 SSH 入口作为回退。完成后，博客再补充实际配置和测量结果；目前上面的结构属于设计方案，不能当作可直接运行的教程。
